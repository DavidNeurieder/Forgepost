If search is central to your platform, you could make text itself addressable.

One concern: granularity

I would stop at the block or paragraph level for the initial implementation.

If every sentence or every word becomes a database row from day one, you'll dramatically increase complexity:

More joins
More indexing
Harder editing logic
More migration work

You can always evolve the model later.

For an MVP, a hierarchy like this is a good balance:

Document

    ├── Section
    │
    ├── Heading
    │

    │

    │
    ├── Code Block
    │
    ├── Quote
    │
    └── Table


Each node is a row in the database, each has its own ID, metadata, version history, analytics, and relationships.

That still gives you all the benefits of structured storage while keeping the system manageable.

PDF
Native mobile views
Desktop views
Search indexes
AI-friendly structured data
Federation payloads

In other words, the database stores the semantic document, and every presentation format is derived from it. That philosophy aligns very well with the broader publishing platform you're envisioning.
