Forgepost

A small blogging engine whose real product is the publish → measure → experiment → improve loop. Every headline, paragraph, image, and call-to-action is a measurable, testable object. One binary. Your server. Your data.

Self-hosted · No Node.js · No database server · AGPL-3.0

Built for the publish → measure → experiment loop

✍️

Thin blog host

A Markdown editor that parses to a block tree, publish/unpublish, tags, image uploads served from /media, Markdown import (drop in an existing .md or a .zip bundling it with its images to create a reviewable draft), comments with moderation, RSS, full-text search (SQLite FTS5 with snippet highlighting), and one clean theme. Each block is a first-class, versioned object.

🎬

Video embeds

A line that is exactly one YouTube or Rumble URL — or a raw <iframe> line — becomes a video block. Click-to-load rendering: a lazy thumbnail with zero third-party requests until the reader chooses to play, plus og:video and a JSON-LD VideoObject.

📊

Per-block analytics

Privacy-lean browser tracking — scroll depth, completion, read time, impressions — with estimated reach and drop-off per block. Honestly labeled, because blockers undercount.

🧪

Block experiments

A/B test alternative content on any block. Stable per-visitor traffic split, impression/conversion tracking, and a Bayesian sequential test with exact P(beats control).

⚖️

Stopping rules that decide

Credible intervals, a spending-bound-corrected confidence threshold, and a no-winner stop rule. Promote the winner automatically — no hand-waving, no p-hacking.

📦

One binary, solo mode

Single forgepost binary with embedded SQLite. Argon2 password hashing, session cookies, CSRF protection, and a rate-limited analytics API. forgepost backup create seals the database + media into a self-verifying .fpb archive (verify / restore with a rollback), and forgepost demo installs a ready-made blog with a live experiment.

🔒

HTTPS built in

In-process TLS: automatic Let's Encrypt issuance and renewal, or bring-your-own certificates that reload on change. No reverse proxy required.

📚

Read next

Every article ends with up to three related-post cards, ranked by shared tags (most recent posts backfill the list). Impressions and clicks are tracked into analytics to feed a future personalized recommendation engine.

🎯

Game-feel dashboard

The admin dashboard opens with the week's most-read post, a per-post Views (7d) column with a Δ vs last week signal, and a nudge pointing at the post with the worst read-through — keep the loop moving.

🧭

Traffic sources & shares

The Stats page buckets each article's views into Search / Direct / Community from the captured referrer, and a Share button on every article (native sheet or clipboard copy) reports share_click events shown as a Shares stat.

How the loop works

1

Write

On the dashboard, click New post (or Import post to bring in an existing Markdown file or a .zip of markdown plus images). The editor stores Markdown and renders a live block preview. The first block is the headline; every paragraph, image, and CTA becomes its own block.

2

Publish

The post appears on the public route and the RSS feed. Saving sets a stable URL from the title while the post is still a draft — once published, the URL never changes.

3

Measure

Open Stats for a document: views, unique readers (estimated), average reading time, completion, shares, a scroll-depth funnel, a per-block drop-off table, and a traffic-sources breakdown (Search / Direct / Community) — where do readers leave, and how did they get here?

4

Experiment

On the Stats page, pick the block to test, choose what share of visitors see variants, and add replacement content. Control is created automatically.

5

Watch and decide

The live report shows impressions, conversions, conversion rate, and P(beats control) per variant as the posterior updates. Decide manually or let the background auto-decider apply the sequential-test rules.

6

Promote

A decision repoints the live block to the winning immutable version, so the article changes immediately. Rinse and repeat.

Get started in two minutes

Build the single binary, then either install the demo blog or run your own setup. No Node.js in production, no database server, no config files for 90% of installs.

# Build the release binary
cargo build --release --bin forgepost

# The one-command quick start: installs 6 demo articles + a live
# headline experiment, then serves on http://127.0.0.1:8080
./target/release/forgepost demo
#   login: admin@example.com / demo-password  →  http://127.0.0.1:8080/admin

# Or start your own blog (creates forgepost.db, runs migrations)
./target/release/forgepost serve
# Open http://127.0.0.1:8080 → /setup wizard, then write your first post

# Backups: seal the database + media into a self-verifying .fpb archive
./target/release/forgepost backup create
./target/release/forgepost backup restore forgepost-<ts>.fpb --yes

# Automatic HTTPS
./target/release/forgepost serve --tls-domain example.com --addr 0.0.0.0:443

# Bring-your-own certificates (reloaded on change)
./target/release/forgepost serve --tls-cert cert.pem --tls-key key.pem --addr 0.0.0.0:443

The tests that keep it honest

cargo test --workspace                     # engine golden + property tests, API, pages
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
cd e2e && npm run test:e2e                    # real browser vs the real binary

The experiments crate's correctness is checked with hand-computed beta golden tests plus property tests — posterior sanity, sample-size concentration, and no-winner/stop correctness. The auto-decider promotes a variant only once it clears the spending-bound-corrected threshold.
