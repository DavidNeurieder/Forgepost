Forgepost

A small blogging engine whose real product is the publish → measure → experiment → improve loop. Every headline, paragraph, image, and call-to-action is a measurable, testable object. One binary. Your server. Your data.

Self-hosted · No Node.js · No database server · AGPL-3.0

Built for the publish → measure → experiment loop

✍️

Thin blog host

A Markdown editor that parses to a block tree, publish/unpublish, tags, comments with moderation, RSS, and one clean theme. Each block is a first-class, versioned object.

📊

Per-block analytics

Privacy-lean browser tracking — scroll depth, completion, read time, impressions — with estimated reach and drop-off per block. Honestly labeled, because blockers undercount.

🧪

Block experiments

A/B test alternative content on any block. Stable per-visitor traffic split, impression/conversion tracking, and a Bayesian sequential test with exact P(beats control).

⚖️

Stopping rules that decide

Credible intervals, a spending-bound-corrected confidence threshold, and a no-winner stop rule. Promote the winner automatically — no hand-waving, no p-hacking.

📦

One binary, solo mode

Single forgepost binary with embedded SQLite. Argon2 password hashing, session cookies, CSRF protection, rate-limited analytics API, and forgepost export for backups.

🔒

HTTPS built in

In-process TLS: automatic Let's Encrypt issuance and renewal, or bring-your-own certificates that reload on change. No reverse proxy required.

How the loop works

1

Write

On the dashboard, click New post. The editor stores Markdown and renders a live block preview. The first block is the headline; every paragraph, image, and CTA becomes its own block.

2

Publish

The post appears on the public route and the RSS feed. Saving sets a stable URL from the title while the post is still a draft — once published, the URL never changes.

3

Measure

Open Stats for a document: views, unique readers (estimated), average reading time, completion, a scroll-depth funnel, and a per-block drop-off table — where do readers leave?

4

Experiment

On the Stats page, pick the block to test, choose what share of visitors see variants, and add replacement content. Control is created automatically.

5

Watch and decide

The live report shows impressions, conversions, conversion rate, and P(beats control) per variant as the posterior updates. Decide manually or let the background auto-decider apply the sequential-test rules.

6

Promote

A decision repoints the live block to the winning immutable version, so the article changes immediately. Rinse and repeat.

Get started in two minutes

Build the single binary, run it, and finish setup in the browser. No Node.js in production, no database server, no config files for 90% of installs.

# Build the release binary
cargo build --release --bin forgepost

# Start the server (creates forgepost.db, runs migrations)
./target/release/forgepost serve

# Open http://127.0.0.1:8080 → /setup wizard, then write your first post

# Backups / migration path
./target/release/forgepost export --output db.json

# Automatic HTTPS
./target/release/forgepost serve --tls-domain example.com --addr 0.0.0.0:443

# Bring-your-own certificates (reloaded on change)
./target/release/forgepost serve --tls-cert cert.pem --tls-key key.pem --addr 0.0.0.0:443

The tests that keep it honest

cargo test --workspace                     # engine golden + property tests, API, pages
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
npm run test:e2e                            # real browser vs the real binary

The experiments crate's correctness is checked with hand-computed beta golden tests plus property tests — posterior sanity, sample-size concentration, and no-winner/stop correctness. The auto-decider promotes a variant only once it clears the spending-bound-corrected threshold.
